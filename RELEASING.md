# Випуск нової версії

Операційна інструкція для цього репозиторію. Про **налаштування з нуля** в новому проєкті —
окремий документ, [DEPLOYMENT_PLAYBOOK.md](DEPLOYMENT_PLAYBOOK.md).

---

## Три команди

Замініть `0.1.2` на потрібну версію.

```bash
node scripts/sync-version.mjs 0.1.2
```

```bash
git add -A && git commit -m "release 0.1.2" && git push
```

```bash
git tag v0.1.2 && git push origin v0.1.2
```

Усе. Далі нічого робити не треба — ні на GitHub, ні локально.

**Який номер брати.** Виправлення й дрібні зміни — третя цифра (`0.1.1` → `0.1.2`). Нові
можливості — друга (`0.1.2` → `0.2.0`). Ломані зміни — перша.

**Чому не можна правити версію руками.** Вона живе в дев'яти файлах: шість `package.json`,
`tauri.conf.json`, `Cargo.toml` і `Cargo.lock`. Джоба `Validate Version Consistency` звіряє їх
усі між собою **і з іменем тега** — розбіжність зупиняє реліз одразу. `sync-version.mjs` оновлює
всі дев'ять за один раз.

## Що станеться само

| Коли | Що |
|---|---|
| відразу | `Validate Version Consistency` звіряє версії з тегом (~15 с) |
| далі | чотири збірки паралельно: Windows x64, Linux x64, macOS arm64, macOS x64 |
| ~5–13 хв | створюється реліз `v0.1.2` з інсталяторами, підписами й `latest.json` |
| +40 с | джоба `deploy-site` перебудовує сайт із новими посиланнями |
| при старті додатка | встановлені копії бачать `latest.json`, показують банер оновлення |

Перша збірка після довгої паузи довша (~13 хв, холодний кеш Rust), наступні — близько 5 хвилин.

## Як переконатися, що вийшло

Три перевірки, зверху вниз. Якщо третя проходить — працює все.

**1. Реліз з файлами**

https://github.com/SpiritUrban/git-manager/releases/latest — має бути `.exe`, `.msi`, два `.dmg`,
`.AppImage`, `.deb`, `.rpm`, і поруч `latest.json`.

**2. Манифест оновлення** — саме ця URL опитується додатком:

```bash
curl -s -L https://github.com/SpiritUrban/git-manager/releases/latest/download/latest.json | head -5
```

Мусить віддати JSON із новою версією. Якщо 404 — реліз не дійшов до кінця.

**3. Сайт**

```bash
curl -s https://spiriturban.github.io/git-manager/download-manifest.json
```

Поле `version` мусить дорівнювати новій версії. Якщо стара — `deploy-site` не відпрацював.

## Якщо впало

**Дивіться анотації, а не логи.** Логи ранів вимагають входу в акаунт, а анотації публічні — і в
них навмисно виводиться повний хвіст помилки збірки. Відкрийте впалий ран, розділ **Annotations**,
блок `Build output`.

**Реліз не створився** (збірки впали до публікації) — виправляйте й переставляйте той самий тег:

```bash
git add -A && git commit -m "fix release" && git push
```

```bash
git tag -f v0.1.2 && git push --force origin v0.1.2
```

**Реліз уже створився** — тег **не рухайте**. Випускайте наступну патч-версію з початку
інструкції. Переставлений опублікований тег ламає верифікацію оновлень у тих, хто вже завантажив.

---

## Чого не робити

1. **Не правте версію руками** — тільки `sync-version.mjs`, інакше `Validate Version Consistency`
   зупинить реліз.

2. **Не переставляйте опублікований тег.** Дозволено лише поки реліз не створився.

3. **Не чекайте релізу від ручного запуску.** `Actions → Release → Run workflow` — це **димова
   перевірка**: збирає всі чотири платформи, але нічого не публікує і сайт не деплоїть. Зроблено
   свідомо, щоб випадковий клік не створив реліз з тегом `main`. Корисно, коли треба перевірити,
   що збірка жива, не випускаючи версію.

4. **Не втрачайте ключ підпису й пароль до нього** (`TAURI_SIGNING_PRIVATE_KEY` та
   `..._PASSWORD` у секретах репозиторію). Без них підписати оновлення неможливо, а зміна ключа
   означає, що всі встановлені копії перестануть приймати оновлення — доведеться змушувати
   користувачів перевстановлювати вручну.

5. **Не вимикайте `bundle.createUpdaterArtifacts`** у `tauri.conf.json` — без нього не буде ні
   `latest.json`, ні підписів, і автооновлення тихо перестане працювати.

## Коли реліз не потрібен

**Зміни лише на сайті** (`apps/site/**`, `packages/ui/**`, `packages/shared/**`,
`scripts/generate-download-manifest.mjs`) — достатньо пуша в `main`. Воркфлоу Pages має
`paths`-фільтр і передеплоїть сайт сам, за ~40 секунд. Тег не потрібен.

**Зміни в самому додатку** — Rust, фронтенд десктопа, іконки, `tauri.conf.json` — вимагають релізу.
Вони вкомпільовані в `.exe`, тому до встановлених копій доходять тільки через оновлення.

Окремо про іконки: правка файлів у `src-tauri/icons/` **не змінює** іконку вже встановленого
додатка. Потрібен реліз і оновлення. Windows ще й кешує іконки — інколи потрібен перезапуск
explorer, щоб побачити нову.

## Перед тегом (необов'язково, але дешево)

Локальні перевірки — те саме, що робить CI, лише швидше:

```bash
npx pnpm check
```

Це `typecheck` + тести TypeScript + тести Rust. Якщо треба переконатися, що збирається сам
застосунок:

```bash
npx pnpm --filter @git-manager/desktop tauri build
```

Або, щоб перевірити всі чотири платформи не випускаючи версію — ручний запуск `Release`
(див. пункт 3 у «Чого не робити»).

## Дрібниця, яку можна поправити

Опис релізу зараз шаблонний: `See release notes for Git Manager vX.Y.Z.` Задається в
`releaseBody` у [.github/workflows/release.yml](.github/workflows/release.yml). Якщо захочете
справжні нотатки — або пишіть їх туди, або замініть на генерацію з коммітів.
